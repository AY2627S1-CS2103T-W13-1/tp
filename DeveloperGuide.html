CouchCoach Developer Guide

Value proposition

CouchCoach helps coaches of any sports team keep player details and observations together while comparing players and deciding who to keep or cut. Fast name lookup, custom tags, ratings and selection views support that work through typed commands and a desktop player list. See Product scope for the intended users and boundaries.

Acknowledgements

  • CouchCoach adapts the application structure, code and documentation of SE-EDU AddressBook Level 3.
  • The application uses JavaFX for its desktop interface and Jackson for JSON storage. Tests use JUnit 5.
  • The documentation site uses MarkBind and its PlantUML support for diagrams.

Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

UI component

The API of this component is specified in Ui.java

See the player-card detail for the planned US21 remarks and US13 injury-status display.

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

API : Model.java

The model is shown in four class views: contracts, roster data, identity, and player assessments. Repeated class names refer to the same classes across views. Open the editable HTML diagram. The corresponding PlantUML sources are model contracts, roster data, player identity, and player assessments.

The Model component,

  • stores the team's player data as Person objects, which are contained in a UniquePersonList object.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Each Person (a player) holds one Name, one Phone, one SelectionStatus, one Rating, one Remark, one InjuryStatus, zero or one JerseyNumber, and zero or more Tag values. Empty remarks and unrated ratings are present value objects, so their multiplicity is still 1. These are ordinary associations: immutable values can be shared between player versions, so deleting one player does not imply deleting its value objects. AddressBook exclusively contains its UniquePersonList, which is shown using composition. The full roster and filtered view reference the same player objects; filtering does not create copies.

UniquePersonList uses Person#isSamePerson to reject duplicates: two players are the same if their names match after ignoring case and repeated spaces. Phone numbers, jersey numbers and tags do not affect identity: players such as siblings may share a parent's contact number, and add and edit accept a shared jersey number, only warning the coach about it. Routine accessors, library collection wrappers, and unrelated methods are omitted from the diagrams. The static tag-validation operation is underlined.

Storage component

API : Storage.java

The Storage component,

  • saves the team and the user preferences as JSON files, and reads them back into model objects. StorageManager implements Storage and delegates to one class per file: JsonAddressBookStorage for the team (data/addressbook.json) and JsonUserPrefsStorage for window settings (preferences.json). Both paths are relative to the working directory, i.e. the folder the app is launched from.
  • depends on some classes in the Model component, because its job is to save and retrieve objects that belong to the Model.

JSON adaptation. JsonSerializableAddressBook holds a list of JsonAdaptedPerson, which stores every player field as a String (or a list of String for tags), so that Jackson can map it to JSON directly. Converting back with JsonAdaptedPerson#toModelType() validates each field with the same rules the commands use, e.g. Phone#isValidPhone and Tag#isValidTagName. JsonSerializableAddressBook#toModelType() additionally rejects a null entry in the persons list and two players with the same name (as defined by Person#isSamePerson).

Defaults and backward compatibility. A field that is missing from the file takes the default a new player would have: PENDING selection status, unrated, fit, no tags, an empty remark and no jersey number. Data files saved by earlier versions, which lack the newer fields, therefore still load. Conversely, JsonAdaptedPerson leaves out an unset jersey number when saving, and writes a null rating for an unrated player.

Loading at startup. MainApp#initModelManager reads the team once, when the app starts:

JsonUtil#readJsonFile returns an empty Optional for a missing file, and throws a DataLoadingException for a file that cannot be parsed. JsonAddressBookStorage also turns an IllegalValueException from the conversion into a DataLoadingException, so an invalid file reaches the same fallback whatever is wrong with it: an empty team plus Messages.MESSAGE_DATA_FILE_UNREADABLE, which UiManager shows in the result box. The team file is not written at startup, so the invalid file stays on disk for the coach to fix. An unparsable preferences.json similarly falls back to default window settings.

JsonUtil#readJsonFile also rejects a document containing only null with a DataLoadingException. JsonUserPrefsStorage rejects null GUI settings before preferences reach the model. Invalid preferences fall back to defaults and are rewritten at startup; the team file is unaffected.

Saving after a command. The Model holds the team in memory; the file is only written by LogicManager#execute:

  • LogicManager#isReadOnly lists the command types that never change data (list, find, filter, sort, squad, help and exit). Every other command type saves after it executes successfully, even when it changed nothing (e.g. keep on a player who is already kept). This can save changes from earlier failed attempts.
  • A command that is rejected throws a ParseException or CommandException before the save step, so the file is unchanged.
  • Each save writes the whole team through JsonAddressBookStorage#saveAddressBook, which also recreates a missing data folder via FileUtil#createIfMissing.
  • If the save throws an IOException (e.g. the file or folder is read-only), LogicManager throws a CommandException with LogicManager.MESSAGE_SAVE_FAILURE. The change stays in the in-memory Model, but the save is unsuccessful. FileUtil#writeToFile writes directly to the destination with Files.write, so an I/O failure can leave the file unchanged, empty or partially written. A later successful save writes the whole in-memory team, including all changes whose earlier saves failed.

Design considerations.

Aspect: When to save

  • Alternative 1 (current choice): Save the whole team after every command that may change data.
    • Pros: Simple; each successful save writes the current whole team, including changes from any number of earlier failed saves. Consecutive failures can leave multiple commands unsaved until a save succeeds.
    • Cons: Rewrites the whole file for every change, which is fine for a team-sized roster but would not scale to very large files.
  • Alternative 2: Save only when the app exits.
    • Cons: A crash or a failed final save loses every change of the session.

Aspect: What to do with an invalid data file

  • Alternative 1 (current choice): Start with an empty team, warn, and leave the file untouched until the next change.
    • Pros: The coach can close the app and repair or restore the file without losing it.
    • Cons: A careless change after the warning overwrites the invalid file.
  • Alternative 2: Refuse to start.
    • Cons: The coach cannot use the app at all until the file is fixed outside it.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Jersey number normalization

JerseyNumber validates a numeric value from 0 to 99 with optional leading zeros. The immutable numeric value supplies equality, display, and JSON serialization, so 099 and 99 produce the same stored number and duplicate warning. Validation rejects out-of-range digits before integer parsing, including padded values such as 0100.

Adding players, jersey numbers and duplicate warnings

Implementation

add creates a new Person from a name, a phone number, an optional jersey number and optional tags. The sequence diagram below shows how add n/Amy Tan p/91234567 j/7 is executed.

Note: The lifeline for AddCommandParser should end at the destroy marker (X), but due to a limitation of PlantUML, the lifeline continues till the end of diagram.

  1. AddCommandParser tokenizes the arguments. It also looks for r/ and i/, but only so that ParserUtil#requireNoRemarkOrInjury() can reject them with a message that names the right command. Without this, r/... would be read as part of the value before it, and the error would blame that value instead. n/ and p/ are compulsory, and ArgumentMultimap#verifyNoDuplicatePrefixesFor() rejects a repeated n/, p/ or j/.
  2. ParserUtil parses each value. parseName() collapses repeated spaces with Name#normalize() before checking the allowed characters and the 100-character limit separately, so that each problem has its own message. parsePhone() removes spaces, hyphens, dots and brackets with Phone#normalize() before checking for 3 to 15 digits. parseJerseyNumber() accepts values from 0 to 99 with optional leading zeros, and JerseyNumber stores the value as an int, so 07 and 7 are the same number.
  3. The parser creates the player with new Person(name, phone, tags), which starts as PENDING, UNRATED, FIT and with an empty remark, and sets the jersey number with Person#withJerseyNumber(). A Person stores a missing jersey number as null but exposes it only as an Optional<JerseyNumber> from getJerseyNumber().
  4. AddCommand#execute() rejects the player if Model#hasPerson() finds a player with the same name. This uses Person#isSamePerson(), which compares names with Name#isSameName(), ignoring case and repeated spaces. Otherwise, Model#addPerson() adds the player and resets the filtered list to show the whole team, so the coach sees the new player.
  5. AddCommand then asks two package-private helpers in the logic.commands package for warnings. DuplicateJerseyNumberChecker#getWarning() looks for other players with the same jersey number (Person#hasSameJerseyNumber()), and SimilarNameChecker#getWarning() looks for names that are equal once spaces and punctuation are ignored (Name#isSimilarTo()). Both search Model#getAddressBook(), i.e. the whole team rather than the filtered list, so they also find players hidden by find or filter. Each returns an empty string or a warning line, which is appended to the success message.
  6. LogicManager saves the team through Storage. JsonAdaptedPerson writes jerseyNumber only for a player who has one, and reads a missing field as no jersey number.

edit reuses the same parsing and checks, with these differences:

  • EditPersonDescriptor records whether j/ was given in isJerseyNumberEdited, as a null jersey number can mean either "not given" or "remove it". EditCommandParser#parseJerseyNumberForEdit() turns an empty j/ into null, which removes the jersey number.
  • The duplicate-name check runs only when the new name belongs to another player (!personToEdit.isSamePerson(editedPerson) && model.hasPerson(editedPerson)), so a coach can change the capitalisation or spacing of a player's own name.
  • EditCommand builds the edited player from the old one, so the selection status, rating, remark and injury status are always kept, and so are the tags. The jersey number is kept unless j/ is given. TagCommand reuses the edit descriptor internally to replace tags. If the result equals the old player, the command reports that nothing changed instead of replacing it.
  • The jersey number warning is checked only when the edit includes j/, and the similar-name warning only when the name actually changes. This stops edits to other details from repeating a warning the coach has already seen.
  • Model#setPerson() replaces the player without resetting the filtered list, so the coach can keep editing search results by the same indices.

Design considerations

Aspect: How to handle a jersey number that is already in use

  • Alternative 1 (current choice): Accept it and warn the coach, naming the other players with that number.
    • Pros: Numbers can legitimately repeat, e.g. training bibs at trials, or players from different age groups in one team. Swapping two players' numbers needs one moment where both share a number, which a hard rule would block.
    • Cons: A coach who ignores the warning can end up with two players on the same number.
  • Alternative 2: Reject the command, like a duplicate name.
    • Pros: Every jersey number identifies one player.
    • Cons: Blocks the legitimate cases above, and makes a swap take three commands.

Aspect: What makes two players the same player

  • Alternative 1 (current choice): The same name, ignoring case and repeated spaces. Names that differ only in punctuation or spacing within words, such as TanWei Ming and Tan Wei Ming, are allowed but trigger a warning.
    • Pros: Catches the common mistake of adding the same player twice, while still allowing two players who share a phone number or jersey number. A warning, rather than a rejection, allows names that are spelt differently on purpose.
    • Cons: Two different players with exactly the same name need something added to one name, e.g. Jr.
  • Alternative 2: The same name and phone number.
    • Pros: Two players with the same name can be added without changing either name.
    • Cons: The same player added twice with different contact numbers is not caught.

Aspect: Where the warning checks live

  • Alternative 1 (current choice): Separate helper classes in logic.commands, called by AddCommand and EditCommand after the change is made.
    • Pros: The warning text is command feedback, so the Model stays unaware of it. Both commands share one implementation.
    • Cons: Each check scans the whole team once per command. This is fast enough for the 1000-player limit in the non-functional requirements.
  • Alternative 2: Check inside UniquePersonList when a player is added or replaced.
    • Cons: The model would have to return warnings alongside its changes, mixing presentation into the model.

Player ratings (US12)

RateCommandParser parses rate INDEX RATING into a RateCommand. It validates the positive displayed index and a whole-number rating from 0 to 10. The word unrated, in any letter case, is parsed as Rating.UNRATED instead, so the same command removes a rating. The command checks that the index exists in the displayed list before changing the model. Removing the rating of a player who is already unrated changes nothing.

RateCommand replaces the selected immutable Person with a copy containing the new rating. Name, phone, selection status, tags, remark, injury status and jersey number are preserved. The current filter stays active; an active rating sort may move the player and change displayed indices.

After command execution, LogicManager saves the team through Storage before returning the result. An invalid displayed index raises CommandException before replacement. If saving fails, the update remains in memory and the coach receives the save-failure message.

Rating sort scopes

SortCommandParser accepts sort rating [all|squad] [asc|desc], ignoring letter case for arguments, with scope and direction accepted in either order. A missing scope maps to Scope.CURRENT, preserving the current predicate. Scope.ALL selects all players; Scope.SQUAD installs the shared HasSelectionStatusPredicate.IS_KEPT predicate. Explicit scope selection replaces rather than intersects a previous name/tag/injury filter.

Direction.ASCENDING and Direction.DESCENDING express the requested order. SortCommand applies its comparator to the model's displayed list. Rated players are ordered numerically and unrated players stay last in either direction. ModelManager breaks ties by source insertion order. The roster and saved file are unchanged, and later view commands may replace the chosen scope while retaining the comparator. list clears both filter and comparator. The existing no-scope syntax remains compatible with workflows that sort a search result.

Selection status feature

Implementation

Each Person has a SelectionStatus, an enum with the values PENDING, KEPT and CUT. New players start as PENDING. The keep, cut and pending commands change it, and all three are handled by one SetStatusCommand class, which takes the status to set. AddressBookParser picks the status from the command word and passes it to a SetStatusCommandParser, which parses the index.

The sequence diagram below shows how cut 1 is executed.

Note: The lifeline for SetStatusCommandParser should end at the destroy marker (X), but due to a limitation of PlantUML, the lifeline continues till the end of diagram.

  1. AddressBookParser matches the command word cut, creates a SetStatusCommandParser for CUT, and uses it to parse "1" into a SetStatusCommand.
  2. LogicManager executes the command. The command gets the player p at index 1 of the displayed list from the Model.
  3. As Person is immutable, p.withSelectionStatus(CUT) returns a new Person with every other field (name, phone, rating, tags, remark, injury status and jersey number) unchanged. The command replaces p with it using Model#setPerson().
  4. LogicManager then saves the team through Storage. It decides this by command type: read-only command types, such as find and squad, skip this step, while keep, cut and pending always save.

If the index is out of range, the command throws a CommandException before changing anything. If the player already has the status, the command returns a message saying so and does not replace the player. LogicManager still saves in this case, as it only checks the command type, so this also saves any earlier unsaved changes.

The status is saved in the data file as a selectionStatus field. Data files saved by v1.3 have no such field, so JsonAdaptedPerson loads those players as PENDING.

Viewing the squad. squad is handled by SquadCommand, which does not build a separate list. It sets the Model's displayed-list predicate to HasSelectionStatusPredicate(KEPT), so the squad is simply the kept players in the displayed list. As a result:

  • any active rating sort still applies, because ModelManager keeps its comparator when the predicate changes;
  • keep, cut, pending and delete use the squad's numbering while it is shown, and a player who is cut or marked pending immediately leaves the displayed list;
  • SquadCommand changes no data, so LogicManager lists it as read-only and does not save after it.

Design considerations

Aspect: How to represent the three commands

  • Alternative 1 (current choice): One SetStatusCommand that takes the status to set.
    • Pros: No repeated code. Adding a new status needs a new enum value and command word, a case in SetStatusCommand#getCommandWord(), and a case in AddressBookParser.
    • Cons: The shared class needs a mapping between each status and its command word, which the separate classes would not need.
  • Alternative 2: Separate KeepCommand, CutCommand and PendingCommand classes.
    • Pros: Each class matches one command word, like the rest of AB3.
    • Cons: Three almost identical classes and parsers to keep in sync.

Aspect: How to show the squad

  • Alternative 1 (current choice): A predicate on the displayed list (HasSelectionStatusPredicate).
    • Pros: Reuses the filtered and sorted list that every other view uses, so indices, sorting and the UI need no special handling.
    • Cons: The squad replaces any active find or filter, as the displayed list has one predicate at a time.
  • Alternative 2: A separate squad list kept in the Model.
    • Cons: Two lists to keep in sync whenever a status, a player or the sort order changes.

Aspect: What the list shows after the command

  • Alternative 1 (current choice): Keep the current filter.
    • Pros: A coach can find Tan and then mark each result in turn without searching again.
    • Cons: When the filter depends on the status, as in squad, the change can move the player out of the filter. For example, cut 1 while viewing the squad removes that player from the displayed list, and the players below move up one index.
  • Alternative 2: Reset to the full list, like add.
    • Cons: The coach loses their place after every decision.

Custom player tags (US08)

Person holds an immutable set of Tag values. The model class diagram above shows its zero-to-many association with tags. Tags are shared values rather than part of player identity: duplicate detection remains based on the normalized player name. Tag trims surrounding whitespace, collapses internal whitespace, validates the allowed characters and the 30-code-point length limit, and preserves display spelling. Equality and hashing use the same case-folded label, so case variants cannot become separate tags. Tags do not participate in player identity.

AddCommandParser collects initial t/ values through ParserUtil.parseTags. Its LinkedHashSet keeps the first spelling among case-insensitive duplicates. TagCommandParser parses tag INDEX t/TAG [t/TAG]...: supplied labels replace the entire set, and a single empty prefix clears it. Missing prefixes and empty labels mixed with other labels fail before any field changes. EditCommandParser rejects tag prefixes with migration guidance before changing any fields; its public syntax accepts only name, phone and jersey edits. Replacement makes the requested final categories explicit; it does not append labels or remove one label by name.

TagCommand delegates player replacement to an EditCommand containing only a tag replacement descriptor, sharing field preservation and filter handling. TagCommand.execute and EditCommand.execute resolve the index against Model#getFilteredPersonList, which exposes the displayed, possibly sorted view. It creates a replacement Person, preserving fields omitted from the descriptor, including rating, selection status, remark, injury status and jersey number. The descriptor and player defensively copy tag sets so later caller changes cannot mutate a stored player. Model#setPerson replaces the roster entry without resetting the predicate or comparator. A player whose new tags no longer satisfy the active filter disappears; the remaining displayed indices change accordingly.

The edit no-change check compares tag spellings as well as Person equality: case-only spelling changes must still be applied. TagCommand formats successful replacements as Updated tags for NAME: LABELS and removals as NAME: tags cleared., retaining the shared No changes made result for an identical replacement. LogicManager saves after a successfully executed tag command, including a no-change result; parse and execution failures do not save. A save failure leaves the in-memory change applied and reports the save warning instead of ordinary edit feedback.

JsonAdaptedPerson writes tag strings in case-insensitive alphabetical order and accepts missing/null tags from older records as an empty collection; invalid/null entries are rejected. PersonCard displays tags alphabetically in a wrapping FlowPane. Keeping tags as immutable values shared by parser, model and storage gives updates and filtering the same label rules without coupling identity to a coach's changing categories.

Filtering players by tag (US16)

FilterCommandParser accepts repeated t/ arguments and reuses ParserUtil.parseTags. It also accepts one optional i/ injury status and requires at least one condition. TagsContainAnyPredicate holds a defensive copy of the requested tags and matches any complete label using Tag equality (OR). FilterCommand#matches combines that result with the optional injury status using AND. An injury-only filter needs no tag predicate. Invalid labels, an invalid/repeated injury status or unexpected preamble fail before the view changes.

FilterCommand replaces the model's list predicate, so each filter searches the full roster rather than intersecting with an earlier name search, filter or squad view. LogicManager treats filtering as read-only and skips saving, including when the data file is unreadable or unwritable.

This partial UML shows the tag-matching path; the optional injury-status condition is omitted. The parser creates the command and optional tag predicate. The predicate realizes Predicate<Person> and reads player tags; the command changes the filtered view through Model.

ModelManager wraps the roster in a FilteredList, then a SortedList, and exposes an unmodifiable observable view. Changing the predicate retains the active rating comparator. Results therefore use rating order when sorting is active, otherwise insertion order, and are numbered from 1. find, filter and squad replace one another's predicate while retaining sorting; list clears both predicate and comparator. This separates a coach's view from persisted roster order and avoids changing records just to browse a group.

Name search implementation (F3 / US04)

AddressBookParser dispatches find to FindCommandParser, which rejects an empty argument string and splits plain keywords on whitespace. NameContainsKeywordsPredicate accepts a player if any keyword matches a whole whitespace-delimited word of the original name or a complete part separated by punctuation. It uses StringUtil.containsWordIgnoreCase for both representations. Thus both Wei-Ming and Ming match Tan Wei-Ming, while Min does not. Letters, combining marks and numbers stay together when punctuation is replaced by spaces; slashes in keywords remain literal, so s/o can match the original name.

FindCommand calls Model#updateFilteredPersonList, using the same filtered/sorted view described above. Each new search covers the whole roster, ignores phone/tag/remark fields, shows each match once, and returns singular or plural match-count feedback. Zero matches is a successful empty view. LogicManager skips saving; invalid syntax leaves the previous view unchanged. Predicate-based matching keeps search independent of JavaFX cards and storage while allowing indexed commands to act on exactly the displayed results.

Appendix: Requirements

Product scope

Target user profile:

  • is a coach of a sports team, at any level (e.g. school, club or community team)
  • has a significant number of players to keep track of, especially during trials or team selection
  • needs to record details and observations about each player
  • needs to rank players and decide who to keep or cut from the team
  • prefers desktop apps over other types of applications
  • can type fast
  • prefers typing to mouse interactions
  • is reasonably comfortable using CLI apps

Value proposition:

CouchCoach brings player contact details, jersey numbers, categories, observations, ratings and selection decisions into one local roster. Coaches can find a player quickly, review a tagged group and compare players before finalising their squad.

Boundaries:

  • The product supports recording players and observations, organising the trial pool, comparing ratings and recording selection decisions, from intake through the final squad list.
  • It is a single-user desktop application for coaches of any sports team. Match-day tactics, training-plan design, contacting players and shared concurrent editing are outside the product scope.
  • Player records are saved locally. The current release does not implement undo/redo, data archiving, partial-string name search, emergency contacts, pagination, statistics or squad export. Historical brainstorms in the team notes are not promises of release functionality.

Use cases

For all use cases below, the System is CouchCoach and the Actor is the Coach, unless specified otherwise.

These use cases describe player-management workflows. The original MVP covered deletion; editing, categorisation, ratings, selection decisions and remarks are now implemented too. Consult each feature's implementation and manual checks for supported syntax and limits.

The following rules apply throughout:

  • A player selected from a displayed list refers to a player in that list, which may contain all players or only search results. For deletion, selection uses the player's current index in the displayed list.
  • Duplicate-name detection is part of the MVP. Names are compared after trimming leading and trailing spaces, collapsing repeated internal spaces, and ignoring letter case. Players may share a contact number.
  • Editing preserves the same name-uniqueness rule: changing a player's name must not duplicate another player's name.
  • Rejected requests leave player data unchanged and do not trigger a save.
  • Successful data changes are saved automatically. If saving fails, the change remains applied in the current session, and CouchCoach warns that the change has not been saved and may be lost after closing.

Non-Functional Requirements

These are acceptance targets, not claims that every platform, performance or display-scale combination has been measured. Record the OS, Java version, dataset and results when validating them. Automatic saving is functional behavior covered by US06 and the saving tests; a failed save cannot guarantee durable data.

  1. Compatibility: The packaged application should run on Windows, Linux and macOS with the supported Java 25 installation described in the User Guide. Verify startup and core commands on each platform; do not assume every newer Java release is compatible.
  2. Responsiveness: With up to 1000 valid player records loaded, each ordinary command should display its result within 2 seconds on a computer meeting its OS's minimum requirements. Measure from command submission to the updated result/list, excluding application startup and externally blocked disk I/O.
  3. Keyboard usability: After launching the app, a coach should be able to add, find, categorise, rate and select players, obtain help and exit through the command box without opening a menu. Check the documented normal workflow with keyboard input.
  4. Single-user operation: The application should be usable by one coach on one computer. Simultaneous processes editing the same data file are outside the supported operating conditions.
  5. Offline operation and privacy: Core roster-management commands should work with the network disconnected and should not transmit player data to a remote server. Opening external documentation links may require a connection.
  6. Storage portability: Player records should use a local, readable JSON text file without a database server. A valid saved roster should reload with its field values intact. Manual file editing still has to satisfy the model's validation rules.
  7. Distribution: The application should be delivered as one JAR of at most 100 MB and run without an application installer, once the required Java runtime is installed.
  8. Display usability: At 1920×1080 with 100% and 125% scaling, command entry, feedback and player details should remain readable without clipped controls. At 1280×720 with 150% scaling, commands and list scrolling should remain usable. Include long tags, names and remarks in these checks.

Glossary

  • CLI (Command Line Interface): A text-based interface in which the user types commands to interact with the app
  • GUI (Graphical User Interface): The visual interface of the app, which displays the player list and command results
  • Coach: The user of CouchCoach, who manages the players of a sports team
  • Player: A member or prospective member of the Coach's team whose details are recorded in CouchCoach
  • Roster: All player records stored by CouchCoach, including players hidden by the current view
  • Displayed list: The roster view selected by the latest list, find, filter or squad, ordered by the active rating sort or insertion order. Help temporarily replaces the visible cards without changing the underlying player view
  • Index: A player's position in the displayed list, starting from 1. It can change after filtering, sorting or modifying players; it is not a permanent player identifier
  • Duplicate name: A player name that matches an existing player's name after trimming leading and trailing spaces, collapsing repeated internal spaces, and ignoring letter case
  • Tag: A custom player category, such as a position, role or trial group. Labels are normalized for whitespace and compared ignoring case; a tag is independent of selection or injury status
  • OR matching: A player matches if any requested name keyword or any requested tag matches; the player is still listed only once
  • Rating: An integer score from 0 to 10. Unrated means no score has been assigned and is distinct from a score of 0
  • Selection status: A player's pending (undecided), kept (selected) or cut (not selected) decision
  • Squad: The roster view containing all players whose selection status is kept
  • Injury status: A player's fit or injured status, independent of selection status and rating
  • Remark: A free-text note that the Coach records about a player to retain qualitative observations
  • JSON: The plain-text data format used for local player storage; changing it by hand requires valid syntax and valid player fields
